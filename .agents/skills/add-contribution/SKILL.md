# Add Portfolio Contribution

Develop a professional contribution from the owner's account through the existing
editorial standard. Support an information-only stage or implementation according
to the current request and authorization.

## Establish the working context

Resolve paths against this repository's root, not the shell's current directory.
Read [AGENTS.md](../../../AGENTS.md) and the
[contribution workflow](../../../docs/contributions/README.md). The workflow is the
source of truth for intake, public wording, presentation and verification; do not
duplicate its rules in another template.

Inspect `content/contributions/types.ts` and the relevant case notes. When
preparing public content, also inspect the current bilingual records and shared
renderer and existing visual components. Use the relevant example: Yunex for a
multi-capability tool, or the wallet case for a changed journey and cross-component
integration. Neither defines required technologies or a fixed capability count.

## Gather and organize the contribution

- Reuse facts and preferences already supplied in the conversation or case notes.
  Ask small groups of targeted questions only for gaps that affect the narrative.
  Accept informal answers in either language; write internal notes in English.
- Establish the problem and users, personal ownership versus team/platform work,
  the complete solution, key decisions, validation and team/business value.
  Check for maintenance, automation and operational work that a short description
  might miss. Do not reduce a multi-purpose contribution to its best-known feature.
- When behavior changes, clarify the before/after sequence and ambiguous outcomes
  using the workflow's intake guidance. Confirm ownership by component and separate
  the initial delivery, later enhancements and reuse by others where relevant.
- Update `docs/contributions/<id>.md` with confirmed facts, qualitative observations
  and unresolved details. Distinguish delivered capabilities, observed outcomes
  and intended benefits. Do not infer metrics, guarantees or exclusive ownership.
- Supporting screenshots, links and exact dates are optional. A firsthand account
  can support a case; keep unknown details out of public claims. Do not add a
  generic public disclaimer about missing records or invent supporting material.
- Honor any requested content-review stage. If the user asks to organize the case
  first, stop at that deliverable with focused follow-up questions where needed.
  If integration is already authorized, continue without requesting permission
  again solely because this skill is being used.

## Prepare and integrate the public case

Follow the workflow's content contract and existing page order. Present the
overview, ownership, value for the team and every substantial capability visibly;
put deeper context, decisions, validation and examples in the shared disclosures.
Separate background supplied for understanding from public copy; retain details
that explain the problem, decisions or value. Choose comparisons, diagrams or
screenshots according to what they clarify, following the workflow's visual
criteria and reusing the current components and gallery behavior.

Maintain the shared case identifier and editorial order, populate both language
records, and align nested identifiers across English and Spanish. Optional
diagrams and references should remain absent when unnecessary, without empty
placeholders. Keep experience references concise and reuse the existing renderer;
adding a normal case should not require a special route or component.

## Verify and refine

Use the contribution workflow's relevant checks. Notes-only work needs editorial
and documentation checks; UI or contract changes need the corresponding lint,
type, build and browser validation. Check language parity, core capability
coverage, attribution, team value and navigation. Check every case-index link and
stable anchor, including direct visits and language changes.

Report what changed, the validation performed and any remaining factual gaps.
Follow repository rules for commits, pushes and deployment. When owner feedback
reveals a reusable improvement, update the standard or this skill in the same
authorized scope. Keep current guidance concise instead of accumulating a history
of corrections or turning one case's details into universal requirements.
